## Запуск

Для разработки — как раньше, три терминала:

```sh
npm install
npm run db:up      # PostgreSQL в Docker на 5433
npm run dev:api    # API на http://localhost:3001
npm run dev:web    # сайт на http://localhost:3000
```

Старую базу удалять не нужно: новые таблицы и колонки добавляются через `ALTER ... IF NOT EXISTS`.

### Если при старте появилось предупреждение про телефоны

Уникальный индекс на телефон не создаётся, если в базе уже есть дубли, и миграция честно об этом
говорит вместо того, чтобы молча править чужие данные:

```
WARNING: customers_phone_digits_key not created: 1 phone number(s) are used by more than one customer.
```

Дубли оставили прошлые прогоны тестов — они регистрировали все аккаунты с одним номером. Разовая уборка:

```sh
psql postgres://food:food@localhost:5433/food_delivery -f apps/api/sql/cleanup-test-accounts.sql
```

Скрипт трогает только адреса вида `e2e-…@example.test` и показывает, что удаляет. Пока индекса нет,
уникальность всё равно соблюдается — её проверяет `UniquenessService` на уровне сервиса.

### Запуск как на сервере

```sh
JWT_SECRET=$(openssl rand -base64 48) docker compose -f docker-compose.prod.yml up --build
```

Три контейнера в одной сети: база, API и сайт. Наружу выходит только сайт на 3000 — ни порт базы, ни
порт API не публикуются, потому что браузер к ним и не обращается.

## 1. Языки

Английский, русский и казахский. Переключатель в шапке, выбор хранится в аккаунте (`users.preferred_language`)
и в браузере, поэтому язык едет за человеком на другое устройство.

Все строки лежат в одном файле `apps/web/src/i18n/dictionaries.ts`. Английский словарь задаёт тип
`Dictionary`, поэтому **забытый перевод — ошибка компиляции**, а не находка пользователя. Сверх того три
теста сравнивают словари между собой: одинаковый набор ключей, никаких пустых строк и одинаковые
подстановки `{count}` — перевод, потерявший `{count}`, показал бы фразу с дыркой.

API отвечает по-английски, но каждый ответ несёт короткий код (`phone_taken`, `weak_password` и так
далее), и частые коды переведены на клиенте. Незнакомый код показывает английскую фразу сервера — это
полезнее, чем «что-то пошло не так».

## 2. Мобильная версия

Шапка на узком экране сворачивает навигацию в одну кнопку и открывает тем же списком — список один,
поэтому две версии не разъезжаются. Таблицы прокручиваются вместо того, чтобы сжимать колонки в кашу, а
история бонусов на телефоне показывается карточками. Фильтры истории складываются под кнопку.
Добавлен `viewport` с реальной шириной — без него телефон рисует страницу в десктопной ширине и ужимает.

## 3. Профиль и поле регистрации

`/profile` — имя, телефон, адрес, язык и смена пароля; у персонала только имя и язык, потому что
доставку получают клиенты. **Email и роль изменить нельзя**: email определяет аккаунт и по нему ищется
ссылка сброса, а роль выдаёт администратор. Отдельный тест отправляет в форму `role: ADMIN` и
`bonusPoints: 99999` и проверяет, что ничего из этого не применилось.

При регистрации появилось поле языка — форма сразу переключается на выбранный.

## 4. Сброс и смена пароля

**«Забыли пароль».** Ответ одинаковый независимо от того, есть такой адрес или нет: форма, отвечающая
«нет такого пользователя», — это способ узнать, кто здесь зарегистрирован.

Почтового сервера в проекте нет, поэтому ссылка пишется в лог сервера, а в режиме разработки
возвращается в ответе — чтобы поток можно было показать целиком. В продакшене в ответе её нет.

**Токен хранится только хешем.** Украденная база не должна содержать работающих ссылок — по той же
причине, по которой в ней нет паролей. Ссылка живёт 30 минут, срабатывает один раз, и запрос новой
гасит предыдущую.

**Выход на других устройствах сделан через версию сессии.** Сначала сравнивали время выпуска токена со
временем смены пароля, но JWT хранит момент выпуска с точностью до секунды: токен, выпущенный в
10:00:00.8, и пароль, смененный в 10:00:00.9, неразличимы, и любое сравнение оставляет окно до секунды.
Поэтому у аккаунта есть счётчик `token_version`: каждый токен несёт номер, смена пароля его повышает, и
все токены со старым номером отклоняются ровно с этого мгновения. Часы в этом больше не участвуют.

Браузеру, который сам сменил пароль, тут же выдаётся новый токен — иначе «сменить пароль» означало бы
«выйти из системы».

## 5. Блокировка по IP

Блокировка аккаунта останавливает подбор пароля к одному человеку. Она ничего не делает против перебора
по списку аккаунтов с одной машины: каждый аккаунт набирает одну-две неудачи, до пяти не доходит никто.
Поэтому неудачный вход считается дважды — за аккаунт и за адрес.

**15 неудач с адреса за 15 минут → блокировка адреса на час.** Порог выше, чем у аккаунта, чтобы
общежитие с одним внешним адресом не блокировало себя обычными опечатками.

Проверка адреса идёт **до** поиска email — перебирающий не должен даже узнать, какие аккаунты
существуют. Администратор видит заблокированные адреса и те, что копят неудачи, но пока не заблокированы,
и может заблокировать или разблокировать вручную.

**Адрес самого сервера заблокировать нельзя.** За прокси сайта все запросы приходят с loopback, и
блокировка выключила бы всех разом, включая администратора, который её поставил.

## 6. Поиск, фильтры и повтор заказа

История ищет по названию блюда, адресу, комментарию и номеру заказа и фильтруется по статусу и датам.
Конец диапазона означает весь этот день целиком — именно это имеет в виду человек, выбирающий «по 5
ноября». Поле поиска с задержкой, чтобы не слать запрос на каждую букву.

**Повтор заказа не копирует корзину вслепую.** Блюдо могло исчезнуть из меню, подорожать или сменить
название, поэтому сервер отвечает, что ещё можно заказать и почём, а человек видит это до того, как
что-то заменит его текущую корзину.

## 7. Новые отчёты

| Отчёт | Отвечает на вопрос |
|---|---|
| По дням | Как идёт торговля: заказы, деньги, средний чек, лучший день |
| По блюдам | Что продаётся, что не заказывали ни разу, какая доля выручки |
| По клиентам | Кто заказывает, как часто, на сколько и с какой оценкой |

Везде считаются только успешные оплаты: отклонённый заказ — это попытка, а не торговля. Выручка по
блюдам берётся по ценам, сохранённым в заказах: прошлые продажи прошли по прошлым ценам, и пересчёт по
сегодняшним выдумал бы деньги, которых не было.

Каждый отчёт выгружается в CSV. Значения с запятой, кавычкой или переводом строки экранируются — блюдо
«Чай, с лимоном» иначе разъехалось бы на две колонки; на это есть отдельный тест.

## 8. Сервер

- `GET /api/health` отвечает, только если доступна база, `GET /api/health/live` — пока жив процесс.
  Инстанс, который запущен, но не видит PostgreSQL, не должен оставаться в балансировке.
- Настройки проверяются один раз при старте: неверный порт, чужой формат `DATABASE_URL` или дефолтный
  `JWT_SECRET` в продакшене останавливают запуск с понятным сообщением.
- `trust proxy` — иначе за прокси сайта все запросы выглядят как пришедшие с одного адреса, и лимит по
  IP мерил бы прокси.
- Заголовки `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`; `X-Powered-By` убран.
- Мягкая остановка: по `SIGTERM` запросы в полёте доигрываются, а не обрываются посреди транзакции.
- Dockerfile в две стадии (компилятор не едет в образ), контейнер запускается не от root, healthcheck
  ходит в `/api/health`.

## 9. Уникальность

| Что | Как сравнивается |
|---|---|
| Email | без учёта регистра |
| Телефон | только по цифрам: `+7 700 111 22 33` и `77001112233` — один номер |
| Название блюда | без учёта регистра и пробелов по краям |
| Попытка заказа, платёж, отзыв | по одному на заказ (с прошлых итераций) |

Каждое правило проверяется дважды: `UniquenessService` спрашивает заранее, чтобы человек увидел «этот
номер уже принадлежит другому аккаунту», а уникальный индекс в базе — гарантия, которая срабатывает даже
при двух одновременных запросах и при прямом `INSERT`. Порядок именно такой: сначала спросить ради
сообщения, индекс — ради правоты.

## Новое в API

| Метод и путь | Роль | Что делает |
|---|---|---|
| `GET /api/health`, `/api/health/live` | все | Состояние сервера и базы |
| `POST /api/auth/password/forgot` | гость | Запрос ссылки сброса |
| `POST /api/auth/password/reset` | гость | Новый пароль по ссылке |
| `POST /api/auth/password/change` | все вошедшие | Смена пароля |
| `GET /api/profile`, `PATCH /api/profile` | все вошедшие | Свои данные |
| `PATCH /api/profile/language` | все вошедшие | Только язык |
| `GET /api/orders/:id/repeat` | клиент | Что из заказа ещё можно заказать и почём |
| `GET /api/reports/daily`, `/dishes`, `/customers` | бухгалтер, админ | Три новых отчёта |
| `GET /api/reports/:kind/export.csv` | бухгалтер, админ | Любой из них в CSV |
| `GET /api/admin/ips` | админ | Заблокированные и подозрительные адреса |
| `POST /api/admin/ips`, `DELETE /api/admin/ips/:ip` | админ | Блокировка и снятие |

Изменились существующие: `GET /api/orders` принимает `search`, `from`, `to` вместе со `status`;
`POST /api/auth/register` принимает `language`; отчёты теперь доступны и администратору.

## Новое в базе

Две таблицы — `password_resets` и `blocked_ips`. Новые колонки: `users.preferred_language`,
`users.password_changed_at`, `users.token_version`. Три уникальных индекса: email, цифры телефона,
название блюда. Индексы для поиска по истории.

## Что осталось за рамками

Ссылки сброса пароля не уходят письмом: почтового сервера в проекте нет, ссылка пишется в лог. Для
публичного запуска нужны HTTPS перед сайтом, настоящая почта и внешний аудит.

Автоматический срок блокировки (15 минут для аккаунта, час для адреса) не покрыт сквозным тестом —
проверка заняла бы столько же времени; арифметика времени проверена модульными тестами, а ручное снятие
блокировки администратором покрыто по HTTP.

Жест перетаскивания по-прежнему проверяется руками: эндпоинты за ним покрыты тестами, а события мыши
требуют браузерного драйвера, которого в проекте нет.
